# Repository notes

- This is a Bun workspace (`apps/*`); run commands from the repository root. `apps/server` and `apps/cli` are separate runnable projects.
- `apps/server/src/index.ts` exports Bun's server configuration with `fetch: app.fetch`; the Hono app lives in `apps/server/src/app.ts`. `bun run dev:server` uses `bun --hot`, while `bun run start:server` runs without hot reload.
- Keep server route groups flat in `apps/server/src/routes/`, one file per group (for example, `chat.ts` and `health.ts`). Each file exports a chained `Hono` app with routes relative to its mount point (`"/"` for the group root). Mount groups in `apps/server/src/app.ts` with `.route("/chat", chatRoutes)` and export `AppType` from the composed app so the CLI's Hono RPC client retains route types. Add future endpoints to the relevant route file or create and mount another group; keep handlers out of `app.ts`.
- Sessions are created by the server. `POST /sessions` creates an empty session (`201 { id }`, UUIDv7). `GET /sessions/:sessionId/messages` returns the stored messages for hydration (validated with `safeValidateUIMessages`). `POST /chat/:sessionId` runs one assistant step: the body is `{ message }` (a single message), the history is loaded from the database, and the reply streams back. A `user` message starts a turn; an `assistant` message is a tool-result continuation and must be the latest stored message (400 otherwise, also 400 if a resent id's role differs). Continuations reuse the assistant id, so one turn is one stored assistant message. Incomplete tool calls are skipped (`ignoreIncompleteToolCalls`). Both `:sessionId` routes validate the param as a UUID (400), return 404 for an unknown session, and share `loadChat` from `apps/server/src/chat-store.ts`. A retry resends an already stored user message: the server cuts the history at that message instead of duplicating it, and returns 409 if the message id belongs to another session. In `toUIMessageStream`'s `onEnd`, `saveChat` makes the stored messages match the final list (upsert by id with `position`, delete messages no longer in it, record `model` on new assistant messages, set the title once). Assistant ids come from `generateMessageId` so the stored id matches the streamed one. Errors are not persisted: when the outcome is not `completed`, only the incoming messages are saved. A failed save is logged and does not affect the response.
- `packages/tools` (`@justcode/tools`) holds the coding agent's tools. Layout: `src/index.ts` (`agentTools`, the definitions sent to the model, plus `ChatUIMessage`), `src/execute.ts` (the local runner), `src/core/` (shared infrastructure: `workspace.ts`, `walk.ts`, `tool-context.ts`, `describe.ts`), and `src/tools/<group>/` with one kebab-case file per tool (`filesystem/read-file.ts`, `shell/bash.ts`, ...) plus that group's private helpers (`shell/run-command.ts`). Each tool file exports a `tool()` definition with input and output schemas but **no `execute`**, plus a module `{ tool, inputSchema, execute(input, { workspace, abortSignal }), describeApproval?, describeInput, describeOutput, previewOutput?, isFailedOutput? }`. `describeInput` (the call's target, e.g. a path; its input may still be streaming, so every field is optional) and `describeOutput` (a short result summary, e.g. `12 lines`) are what the CLI shows next to the call (`describeToolInput`/`describeToolOutput`); return `undefined` when there is nothing useful to show. The optional `previewOutput` returns result lines shown under the call (bash shows the last lines of its output), and the optional `isFailedOutput` marks a successful result that still reports a failure (bash: a non-zero exit code). The optional `describeApproval` makes the CLI ask the user before each call and returns what the prompt shows (`{ title, summary, description? }`). The CLI never special-cases a tool by name: anything tool-specific belongs in its module. The server sends only the definitions to the model; the CLI runs tool calls locally with `executeToolCall` from `@justcode/tools/execute`, which validates the input first. To add a tool: create it in the matching group folder (add a group when none fits), add its definition to `agentTools` and its module to `toolModules` in `src/execute.ts` (typecheck fails if one is missing). Tools throw an `Error` with a model-readable message on failure; the CLI sends it as an `output-error`.
- Guardrail: every tool path goes through `workspace.resolve` (`packages/tools/src/core/workspace.ts`), which resolves symlinks in the deepest existing ancestor and rejects anything outside the root. The CLI's root is its launch directory (`apps/cli/src/lib/workspace.ts`, `process.cwd()`), like other coding agents; there is no env setting. Listing and search skip `.git`, `node_modules`, `dist`, and `build` and never descend into symlinked directories. Do not add a tool that touches the filesystem without going through the workspace.
- `bash` (`tools/shell/`) is the one tool the workspace cannot confine: only its `workdir` is resolved through the workspace. It defines `describeApproval`, so the CLI asks the user before each call (`describeToolApproval`; the prompt is `apps/cli/src/components/tool-approval-prompt.tsx`, and "allow all" lasts for the session). A denial goes back to the model as an `output-error` (`toolDeniedError` in `apps/cli/src/lib/tool-approval.ts`; the AI SDK's `output-denied` state is only for server-run tools), and the transcript recognizes it with `isToolDeniedError`. Stored sessions keep that error text, so changing it makes old denials show as failures. Commands run with `bash -c` in a fresh, non-interactive shell (stdin closed so the TUI keeps the keyboard, pagers, colors, and git prompts off) in their own process group. A timeout (default 2 min, max 10 min), an abort (the chat unmounting), or the command finishing kills the whole group, and groups still running when the CLI exits are killed. Output is stdout and stderr interleaved, ANSI-stripped, and capped at 30,000 characters (first third plus last two thirds). A non-zero exit code is a normal result, not a tool error. Any new tool that can act outside the workspace must also define `describeApproval`.
- For Hono JSON routes, validate request bodies with `@hono/zod-validator` (`zValidator('json', schema)`) and read parsed data through `c.req.valid('json')`; `c.req.json<T>()` only asserts a type and does not validate input. For AI SDK chat requests, use Zod to validate the nonempty message envelope and `safeValidateUIMessages` to check the full `UIMessage` parts before passing the validated messages to `convertToModelMessages`; return 400 for invalid input.
- `packages/db` (`@justcode/db`) owns the Prisma 7 schema. During initial development there are no migration files: the schema is applied with `prisma db push`. Create a baseline migration (`prisma migrate dev --name init` against an empty database) before the first shared or deployed database, and use migrations from then on. It has two entry points: `@justcode/db` (`src/index.ts`) exports only the generated model types (`Session`, `Message`, `MessageRole`), with no runtime code, so any app, including the CLI, can import them with `import type`; `@justcode/db/client` (`src/client.ts`) exports the singleton `prisma` client (`@prisma/adapter-pg`, reads `DATABASE_URL`) and is server-only. `Session` is anonymous (no users); each `Message` row is one AI SDK `UIMessage` whose `parts` are JSONB, ordered by `position`. Validate loaded `parts` with `safeValidateUIMessages` before use. The generated client (`packages/db/generated/`) is gitignored and is created on `bun install` (postinstall) or `bun run db:generate`.
- In all apps, validate data from external or untyped boundaries on the client too (for example, router location state, storage, and network responses) with Zod schemas before using it. Prefer `safeParse` when invalid or absent data needs a fallback; do not rely on TypeScript `as` assertions as validation. Avoid transformations such as trimming when the original user input must be preserved.
- `apps/cli/src/index.tsx` renders an interactive terminal UI with OpenTUI React, not browser DOM components. Its TS config uses `jsxImportSource: "@opentui/react"` (also declared in the entrypoint pragma).
- For OpenTUI work, invoke the `opentui` skill first and consult its React and task-specific references (inputs, keyboard, layout, testing, etc.). Check installed `node_modules` APIs only when the skill does not cover the question or installed-version behavior needs confirmation.
- OpenTUI React is real React with a custom terminal renderer. Its `<textarea>` is imperative, not a controlled React input: it has no `value`/`onChange`, `onSubmit` does not provide the text, and `onContentChange` does not provide the new content. Keep a `TextareaRenderable` ref and read `ref.current.plainText` on submit; use React state for derived UI such as textarea height rather than duplicating its text unless needed.
- Name source files in kebab-case (for example, `home-screen.tsx` and `home-textarea.tsx`), even when exported components use PascalCase.
- In the CLI, keep screen-level layouts in `src/screens/`, UI components in `src/components/`, and stateful hooks in `src/hooks/` (for example, `use-agent-chat.ts` wraps `useChat` with local tool execution); keep `src/index.tsx` focused on renderer setup and mounting the screen.
- CLI routes: `/` (home) creates a session with `POST /sessions` on send and navigates to `/sessions/:sessionId` with the prompt in location state. The chat screen validates the param, hydrates `useChat` from `GET /sessions/:sessionId/messages`, then sends the prompt. Its transport targets `POST /chat/:sessionId` and sends only the newest message (`prepareSendMessagesRequest`); the session id comes only from the URL. `onToolCall` runs agent tools against the workspace (asking for approval first when `describeToolApproval` returns a prompt) and `sendAutomaticallyWhen` resends the assistant message once all outputs are in, capped at `MAX_TOOL_CALLS_PER_TURN` tool calls per turn. In development, `bun run start:cli` runs from `apps/cli`, so that is the workspace; to work on another directory, run `bun <repo>/apps/cli/src/index.tsx` from it.
- Keep the interactive CLI's root script on `bun run --cwd apps/cli start`. `--cwd` runs the script directly from the CLI directory so OpenTUI can control terminal output and keyboard input. Bun's `--filter` is a workspace script runner that can manage/format output; reserve it for non-interactive or multi-workspace scripts rather than full-screen TUI apps. This is a development-script choice, not a requirement for distributing the CLI.

## Commits

- For every commit, consult the `git-commit` skill and choose the message from the actual diff.
- Use Conventional Commit subjects in the format `<type>(<scope>): <imperative description>`. Use a relevant type, omit the scope when there is no useful one, and keep the subject under 72 characters.
- Make the subject specific enough to identify the user-visible or technical change; avoid generic descriptions such as "update feature" or "improve things". Name the affected behavior or capability.
- For every nontrivial commit, include a descriptive body with concise bullets that explain the notable changes in the actual diff (not merely repeat the subject). Choose details from the diff, keep each bullet on its own actual line, and separate the subject and body with a blank line. Never encode line breaks as literal `\\n` text. When using `git commit -m`, pass the body as a multiline shell string or use repeated `-m` options.
- Keep each commit focused on one logical change and stage only the intended files.

## Commands

- Install: `bun install` (the workspace uses `bun.lock`).
- Run the CLI: `bun run start:cli`; run the server: `bun run dev:server` or `bun run start:server`.
- Database: `docker compose up -d` starts local Postgres; set `DATABASE_URL` in `packages/db/.env` (Prisma CLI) and `apps/server/.env` (server), see the `.env.example` files. Schema changes: edit `packages/db/prisma/schema.prisma`, then run `bun run db:push` (applies the schema with `prisma db push`, then regenerates the client; Prisma 7 does not regenerate on push). Changes that drop data need `bunx prisma db push --accept-data-loss` from `packages/db`, and a renamed field is applied as a drop plus an add. `bun run db:reset` wipes all data and recreates the tables from the schema (`prisma db push --force-reset`, no confirmation prompt); `prisma migrate reset` does not apply here because there are no migration files. Inspect with `bun run db:studio`.
- Check all workspaces: `bun run typecheck` (shared, db, tools, server, then CLI). For a focused check: `bun run tsc --noEmit -p apps/server/tsconfig.json` or `bun run tsc --noEmit -p apps/cli/tsconfig.json`.
- There are no configured test or lint scripts; typecheck is the available repository-wide check.
- To exercise routes without a server, call `app.request()` from `apps/server/src/app.ts` under Bun (`bun -e`, run from `apps/server` so `.env` loads). The Hono CLI (`hono request`/`batch`) cannot load this app: it runs a bundled module under Node that cannot resolve the TypeScript `@justcode/db` workspace package.
